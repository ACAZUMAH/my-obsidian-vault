# Bora KYC: an NIA answer the backend does not recognise is a 400, not a 502

Date: 2026-11-09
Source: direct user decision in a `bora-capital-backend` session, staging log evidence the user pasted, NIA's Selfie Verification API document the user supplied, and the code changed and verified in that session (paraphrased).

Staging, 9 Nov 2026: during frontend testing, NIA's yes/no face endpoint answered HTTP 400 with `success`, `code` and `msg` beside `data`, not inside it as the NIA document's sample suggests, and with code `11`. NIA's document lists only codes 00 (verified), 01 (not verified), 02 (invalid data), 03 (watch list) and 04 (NIA internal error). `data` carried `verified`, `onWatchList`, `nationalId` and `person`, so the yes/no endpoint does return the person's NIA record. The backend read the code only from `data`, found none, logged an `UnreadableReply`, and answered 502 "Ghana Card verification is unavailable". The KYC never reached BCL: the error was thrown inside `verifyNiaSelfie`, before `createBclKyc`, and the claim was released.

The app showed "Please don't send it again. Bora received your verification…" because its `createKyc` request failed on the phone with "Network request failed" before the server answered; the app then read `kycStatus` as `SUBMITTED` while the server still held the claim, and treats that as received. The backend cannot change that app message; the app should re-check status before concluding.

User decision: when NIA cannot verify, or answers with something the backend does not know, the customer gets a 400 saying NIA could not verify the card and selfie, not a 502 "unavailable", and the KYC still never reaches BCL. The user also asked the agent to test NIA live with their own Ghana Card number and a photo of them found on their computer. The agent declined to send a government ID and biometrics to NIA itself, and to read `.env` (the user's 2026-10-11 rule), and built a script for the user to run instead.

Implemented: `readNiaSelfieResult` reads the code from `data` or beside it, with a numeric code padded to two digits. A match needs code 00 and `verified` true ("TRUE" in any case, or boolean). Any other NIA answer that carries a code but is not a documented, consistent result returns a null code with the provider code kept. `verifyNiaSelfie` logs it as `UnrecognisedReply` with NIA's code, `msg` (Ghana Card PINs replaced, 200 characters at most), `success` and `verified`, never the record. `verifyKycSelfie` then throws `niaCouldNotVerifyError`, a 400: "NIA could not verify this Ghana Card and selfie. Check the Ghana Card number and retake the selfie facing the camera in good light, then try again." The app's selfie-retake rule matches it. The audit records NIA's code as `reasonCode`. A reply with no code at all, a non-JSON reply, a timeout or a network failure stays 502 "unavailable", and code 04 (NIA's internal error) stays 502.

Test script: gitignored `scripts/nia_staging/testNiaSelfie.ts` with a README. It loads `.env` through dotenv, takes `--pin` and `--image`, converts any photo to a PNG under 1 MB with `sips` as the app does, posts exactly the backend's request, and prints NIA's HTTP status, time, field names, code, redacted message, success and verified, plus the backend's answer. Each run spends one billed NIA check outside the backend's daily limit. The agent dry-ran it against a local fake NIA with a made-up PIN.

Verification: `tsc` clean, `yarn build`, full Jest 193 suites and 1607 tests under Node 26.12.1. Uncommitted at recording. The meaning of code 11 is still unknown.
