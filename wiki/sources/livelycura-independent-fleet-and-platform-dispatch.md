## Core Claims

- Retire the existing company Courier console from Pharmacy Portal and SERLP Mobile.
- LivelyCura Admin owns the delivery network: standalone riders, marketplace/custom-app/manual requests, and dispatch operations fulfilled through SERLP Dispatch.
- Build an independent Fleet product for companies to manage vehicles, drivers/riders, jobs, passenger trips, and company operations.
- A company's participation in LivelyCura delivery fulfillment must be a separate optional integration, not implicit Fleet enrollment.
- Sequence cleanup before the replacement feature.
- Courier has no organization/facility ownership or company management. Retain merchant/order references only for billing and cash remittance.
- The retired company-facing Courier feature was never used in production. Remove it directly; do not preserve it through legacy UI, routes, permissions, migrations, cutover materializers, or reconciliation code.
- Customer, Facility, and Organization are all valid delivery requestors. Their task references describe requestor, order, billing, and remittance context; they do not make Courier riders or fulfillment organization/facility-owned.
- Keep Admin notifications and Courier configuration as separate surfaces. The main-header notification icon opens the signed-in administrator's operational inbox. Courier Configuration remains in Courier navigation and owns platform rider delivery notification settings.
- Admin notification files live directly under `src/notifications`, with the drawer and content at the feature root and supporting components, hooks, helpers, and interfaces in their ordinary subfolders. Do not add a redundant `inbox` ownership layer.
- Rebuild the backend first using established repository architecture, models, services, resolvers, and type-definition conventions. Remove premature Fleet migrations/import machinery; migration work follows feature implementation.

- Fleet people naming must cover both riders and drivers; registration needs fuller personal information than name, phone, qualifications, and generic documents. The custom revision counter on this people model was explicitly rejected. The user did not prescribe an exact replacement label.

- Business/input validation belongs in services; do not introduce custom schema validation/hooks, immutability, or arbitrary length/range constraints. Existing ordinary field metadata remains governed by reference models.
- Archiving must follow existing Departments/MLS behavior (`ARCHIVED` with archive flag, timestamp, actor, and optional reason). INACTIVE deactivation and soft deletion are separate. Inspect established implementations instead of asking the user to choose an already-established convention.

- Fleet schemas omit deletion timestamps and custom revision counters; corresponding Fleet filters and `expectedVersion` contracts must not survive model cleanup. This does not remove fields from unrelated backend domains.

- Fleet services own their database queries and writes. Helper directories contain pure validation and transformation only. Transactions start and end inside the concrete multi-document operation that needs them; do not route ordinary CRUD or unrelated commands through one feature-wide transaction/idempotency wrapper.
- Fleet updates use the owning model's operation-appropriate update method rather than mutating loaded documents and calling document `.save()`. Preserve service validation, transaction scope, atomic operators, audit visibility, and updated return values.
- Fleet operator profiles, lifecycle, and live dispatch state are separate concerns. Live state covers online presence, accepting-work/availability, capacity, and current coordinates through purpose-specific operations; a generic operator update must not own them all.
- Fleet GraphQL follows the established HRM module shape: named thin resolvers call owning services directly, Shield owns endpoint permissions and tenant-context resolution, feature type definitions compose through one interpolated `#graphql` template, and the root resolver map explicitly composes `Query`, `Mutation`, and object types. Do not restore a Fleet-specific principal layer that queries organizations, enabled modules, or facilities.
- Fleet service functions receive one typed object parameter named `data`. Do not pass `{ principal, input }`, positional `input` and user arguments, or a full user document. When an operation needs an actor, the resolver adds only the authenticated user ID to `data`, and the service fetches the user itself.
- Fleet errors name the actual missing record (for example, departure, schedule, or operator) without a redundant Fleet prefix. For scoped errors, say facility when a facility ID is supplied and organization otherwise; do not call the scope a workspace. Apply this across feature slices before advancing to the next feature.
- Inside a Fleet-owned folder, file basenames and function names omit the redundant `Fleet` word (for example, `services/fleet/operators/createOperator.ts` and `createOperator`). The correction also applies to Fleet GraphQL fields/types and Fleet-owned interfaces; rename clients and regenerated types together. Preserve persistence model/collection symbols and the module identifier unless a separate migration requires changing them. List queries follow established filter names and construct both date bounds on the intended record field; interval-based work uses overlap filtering.
- Exception for jobs only (2026-10-10): the Fleet job entity is named `FleetJob`/`fleetJobs` across backend, Pharmacy Portal and SERLP Mobile code, covering folders, files, functions, components, hooks, GraphQL types, operations and inputs, interfaces and enums. Stored references are renamed too: `jobId` becomes `fleetJobId` and the audit entity value becomes `FleetJob`, with no migration because Fleet is pre-production. URLs, deep-link paths, route constant names and visible "Jobs" labels stay unchanged. Departure operations keep their names. Other Fleet entities keep the no-prefix rule.
- Pharmacy Portal Fleet people use the operator name, `fleet.operators.*` permissions, and the actual create/profile/lifecycle/capacity operations. The operator UI follows established list/header/table/hook/modal ownership, keeps one GraphQL operation per hook, and does not restore the rejected driver save operation, custom revision, expected-version, or idempotency fields.
- Operator registration and detail views cover personal, contact, engagement, address, emergency-contact, identity-document, license, qualification, document, and note data. The roster reads online state, availability, current load, capacity, heartbeat, and last coordinates separately; capacity uses its dedicated dispatch operation.
- Expose only Fleet frontend areas whose contracts have been rebuilt and verified. During the one-feature-at-a-time rebuild, unfinished earlier drafts stay out of routing and menus rather than shipping calls to removed backend operations.
- Declare Fleet paths in the Pharmacy Portal's central `routeEndpoints` object and reuse those constants in the app registry, menu, router, redirects, and tests. Do not hardcode Fleet navigation strings or introduce a parallel route flow.
- Fleet operator registration is a protected create page reached from the roster. Its `createOperator` folder owns the page, form components, field editors, interfaces, and create mutation hook. The operator roster folder owns listing and update behavior and must not contain creation-specific files. Do not put registration back into a roster modal or share one create/update form across those flows.
- Fleet create-page inputs include useful field-specific placeholders, including picker, select, numeric, and nested editor fields. Fleet list-header filter inputs use placeholders without visible labels; accessible names remain available to assistive technology. Fleet `useFilters` hooks follow established URL parsing, memoized query values, dedicated callbacks, pagination resets, and reset actions; `page` and `limit` use the Portal's ordinary numeric parsing and defaults, while unselected enum filters stay nullable, are omitted from query variables, and use clearable controls instead of invented `ALL` sentinels. Date-filtered lists use local date-range picker values. Visible Fleet sidebar items and detail tabs have appropriate icons.
- Fleet date and date-time form controls use the existing Mantine `DateInput` and `DateTimePicker` components. Date-range list filters follow established `DatePickerInput` patterns. Bind picker values through owning Formik or URL-filter state; do not substitute `TextInput type="date"` or `type="datetime-local"`.
- Fleet has no generic `src/fleet/shared` layer during the one-feature-at-a-time rebuild. Create and update each own a named Formik/Yup hook, field components, payload transformation, and operation hooks. Pages or modals coordinate submission and navigation; presentation components receive the form and callbacks. Introduce a shared abstraction only after current project code demonstrates stable reuse.
- Fleet operator emergency contacts, identity documents, licenses, and other documents render as accordion sections, with each add action inside its panel. Each editor and profile field component lives in its own file within the owning create or update flow; do not recreate a multi-component profile-editor bundle.
- Fleet operator profile-image fields render the selected image itself after upload. Update forms resolve and display the saved private image through the established temporary document-URL operation, while change and remove actions keep the preview aligned with the Formik upload ID.
- Identity-document sides, license attachments, and other operator documents render inline image/PDF previews. Each upload control owns its loading state so a request affects only the button that initiated it; update forms resolve saved private files through the established temporary document-URL operation.
- Fleet operator details use a protected `/fleet/operators/:id` page owned by `src/fleet/operatorDetails`, not a roster modal. The page displays the operator's business profile, engagement, compliance files, and live work/location state. Keep database, account, organization, facility, and duplicate operator IDs out of the visible record; omit routine created/updated timestamps and inactive archive placeholders, and show archive context only when the operator is archived.
- Apply the same completed feature slice to Fleet vehicles: feature-owned services and GraphQL, central routes, a list, dedicated create page, focused update/archive actions, and a routed detail page with vehicle information, seats, and private-document previews. Keep later draft Fleet screens unrouted until their own backend and frontend pass is complete.
- Pharmacy Portal mounts no Courier route, catch-all, legacy redirect, Courier route constant, or retired-Courier history feature under Billing. `src/billing/legacyDeliveries`, delivery-history routes, menu entries, and permission bridges must remain absent. Merchant/order references stay only on the current Selling, Billing, and platform Courier records and workflows that own them.
- Removing `COURIER` from the current organization `Module` enum must not make login serialization fail on stale stored values. Until data cleanup is deliberately scheduled, the Organization GraphQL boundary returns only persisted values represented by the current enum; this compatibility does not restore Courier module ownership.

Current platform Courier requestor references and unrelated production-domain migrations remain separate.

## Contradictions Or Tensions

The 2026-10-10 jobs decision narrows the earlier rule that Fleet-folder names omit `Fleet`: jobs carry the prefix, every other Fleet entity does not.

Supersedes the earlier product assumption that company fleet management and platform courier fulfillment should use the same company-facing Courier module. It also supersedes the assumption that this retired company feature needs historical-record, balance, obligation, migration, or compatibility preservation: it was preproduction and is removed directly.

The earlier notification-settings removal source records an implementation inference that the user later corrected. The current rule keeps Courier Configuration in Courier navigation while placing the administrator's notification inbox behind the main-header bell; the two surfaces are not interchangeable.
